## 🛠️ Datalium Strata: CLI & Debugging Architecture

To make Datalium Strata the definitive choice for production engineering, it needs an exceptional debugging experience. Python frameworks often force developers to write custom scripts or use clunky web UIs just to see why an agent broke.

The strata CLI will be a single, lightning-fast native binary written in Rust. It will allow developers to query live state, inspect historical checkpoints, and step through agent graphs directly from their terminal.

---

### 🏛️ CLI Design Strategy

- **Universal Portability:** A single binary with zero runtime dependencies. It runs seamlessly on a developer's local machine or inside an enterprise CI/CD pipeline.
- **Machine & Human Friendly:** Supports beautiful, colored terminal outputs (using crates like `clap`, `ratatui`, and `tabled`) along with raw `--json` flags for automation scripts.
- **Language Agnostic Persistence:** Because both the C# and Rust versions of Strata serialize checkpoints into standard formats (e.g., SQLite, PostgreSQL, JSON, or MessagePack), the CLI can parse data stores generated by either runtime.
- **Extensible Command Structure:** A modular command system that can grow as Strata evolves. Initial commands will focus on core debugging needs, with the ability to add new ones for advanced features.

## 📦 Command Architecture & Hierarchy

```bash
strata
├── graph
│   ├── view      # Render a visual ASCII/Unicode representation of the agent graph
│   └── validate  # Run static analysis on code/schemas to find orphan nodes
├── thread
│   ├── list      # List active conversation threads and their current node locations
│   └── inspect   # View thread variables, token usage, and history metrics
├── checkpoint
│   ├── log       # Print a historical timeline of state mutations for a thread
│   ├── diff      # Compare changes in state variables between two sequence IDs
│   └── replay    # Re-execute a specific node using historical state data
```

## 🛠️ UX Command & Output Examples

### 1. Visualizing the Graph Layout

Developers can instantly see how data flows through their architecture without opening a web browser.

```bash
$ strata graph view --path ./src/workflow.json
```

Output:

```text
┌───────────────┐
│     Start     │
└───────┬───────┘
        ▼
┌───────────────┐
│   CallLLM     │◄──────────────────┐ (Transient Error Retry Loop)
└───────┬───────┘                   │
        ▼                           │
┌───────────────┐                   │
│ VerifyResult  ├─(If Invalid)──────┘
└───────┬───────┘
        │ (If Valid)
        ▼
┌───────────────┐
│     End       │
└───────────────┘
```

### 2. Listing and Inspecting Failure Threads

If a production agent crashes, developers can isolate the exact conversation thread and find where it got stuck.

```bash
$ strata thread list --status failed --storage postgres://localhost:5432/strata
```

Output:

```text
┌──────────────────────────────────────┬──────────────┬─────────────┬───────────────────────────┐
│ Thread ID                            │ Current Node │ Sequence ID │ Failed At                 │
├──────────────────────────────────────┼──────────────┼─────────────┼───────────────────────────┤
│ tx_9b1a4c8e-3f2d-41a0-b5e8           │ CallLLM      │ 14          │ 2026-06-20 23:14:02 UTC   │
│ tx_0a2b3c4d-5e6f-7a8b-9c0d           │ ProcessTools │ 3           │ 2026-06-20 18:45:11 UTC   │
└──────────────────────────────────────┴──────────────┴─────────────┴───────────────────────────┘
```

### 3. Analyzing State Diffs

The most powerful debugging feature: seeing exactly how a node mutated the state layout before it threw an exception.

```bash
$ strata checkpoint diff tx_9b1a4c8e-3f2d-41a0-b5e8 --seq-a 13 --seq-b 14
```

Output:

```diff
--- Checkpoint #13 (Node: EntryPoint)
+++ Checkpoint #14 (Node: CallLLM)
 {
   "query": "Optimize indexes...",
-  "response": "",
+  "response": "Error: Context window exceeded or upstream timeout.",
-  "iteration_count": 0
+  "iteration_count": 1
 }

 🛑 EXECUTION HALTED: Node 'CallLLM' threw a Transient Network Exception.
```

### 4. The Developer Superpower: Local Node Replays

Instead of running a massive multi-minute graph to reproduce a bug, a developer can download the exact checkpoint state from production and replay just the single failing node locally.

```bash
$ strata checkpoint replay tx_9b1a4c8e-3f2d-41a0-b5e8 --sequence 13 --local-override-model gpt-4o-mini
```

Output:

```text
🔄 Loading historical state from Checkpoint #13... Done.
🛠️ Overriding LLM Target to: gpt-4o-mini
🚀 Executing Node [CallLLM] locally...

✨ Success! Node completed in 242ms.
📦 Updated State Preview:
 {
   "query": "Optimize indexes...",
   "response": "Indexing optimization completed successfully.",
   "iteration_count": 1
 }
```

## 💎 Key CLI Advantages Over Python Tools

- **Zero Environment Hell:** You don't need to configure `venv`, `pip`, or matching Python runtimes to debug. You drop the `strata` binary onto your machine, point it to your data store, and start inspecting.
- **Blazing Fast Performance:** Querying logs or calculation graphs through millions of database checkpoints takes milliseconds due to Rust's native asynchronous database drivers (the CLI reads through `strata-memory`'s async stores since `design/19-Async-Queryable-Store.md`).
- **CI/CD Integration Ready:** Easily write automation checks like `strata graph validate --path ./src` into your deployment pipelines to ensure developers never ship broken or cyclic graph patterns.
- **Unified Debugging Experience:** Whether your production agents are running the C# or Rust version of Strata, the CLI can parse their checkpoints and provide a consistent debugging interface.

## ✅ Implementation Status: `strata graph validate` (as of demo 14, 2026-09-21)

This section covers `graph validate` only. It reads **graph-definition JSON** (`schema/graph-definition.schema.json`), not source code, so `--path ./src` in the pipeline example above means a folder of exported `.json` files, not a folder of C# or Rust.

**Built:**

- **A file or a directory.** `--path` takes one graph definition, or a directory, in which case every `*.json` file under it is checked (recursively, sorted by path, so the report is the same on every machine). Every file is reported, not just the first failure. Symlinked directories are not followed; files without a `.json` extension are ignored.
- **Exit codes.** `0` every graph valid; `1` at least one graph has structural errors; `2` something could not be checked: a file that is unreadable or is not a graph definition, a path that does not exist, or a directory with no `*.json` files in it. Since SG-09 (`design/22-Graph-Structure-In-Definitions.md`), "not a graph definition" includes a `schema_version` this build doesn't know (`1.0.0`, `1.1.0`, since SG-07/08 `1.2.0`, and since SG-06 `1.3.0` are known), a `kind` in a `1.0.0` level, a `map` below `1.3.0` (`design/27-Map-Fan-Out.md`), a node whose `kind` doesn't match its fields (a group without `branches`, `graph` on a plain node, `branches` on a map, ...), and a `join` below `1.2.0`, on anything but a group or a map, or with a `count` or `condition` its policy doesn't have (`design/26-Parallel-Group-Controls-And-Joins.md`), at any level; `view` refuses the same files, annotates a group's join, and annotates a map with its template's entry point, size and join. A map's template is validated with its nodes named `<map>/*/<node>`. `2` outranks `1` (a gate that could not look at something should not read as an ordinary rejection), and an empty directory is an error rather than a vacuous pass.
- **Output.** Human output lists each file (`OK` / `FAILED` / `ERROR`) with its `[CODE] node -> related: message` lines and a one-line summary. `--json` keeps the single-file shape (`valid`, `entry_point`, `errors[]`) unchanged, and for a directory emits `valid`, `checked`, `valid_count`, `invalid_count`, `unreadable_count` and `graphs[]` (one entry per file: `path`, `valid`, then `entry_point` and `errors[]`, or `error` for an unreadable file).
- **Getting the file from code.** Rust `StateGraph::to_definition()` / `CompiledGraph::to_definition()`, .NET `StateGraph<T>.ToDefinition()` / `CompiledGraph<T>.ToDefinition()` (`Datalium.Strata.Storage.Schema`). The export **does not validate**, so a graph `.compile()` would reject can still be written out and gated. It is the same view `.compile()` validates: nodes in declaration order, the edges in the order added, then each recovery-policy fallback as a guarded `on_failure` edge. Both engines write byte-identical JSON for the same graph (`schema/fixtures/graph-export/`).
- **Same verdict as `.compile()`.** The CLI and both engines call the same validator, and for every case in the parity tests (`graph_export.rs`, `GraphExportTests.cs`) the CLI reports exactly the diagnostics `.compile()` does.
- **Groups and subgraphs are checked inside** (SG-09, `design/22-Graph-Structure-In-Definitions.md`). The export describes a parallel group (`kind: "parallel_group"`, its `branches`) and a subgraph (`kind: "subgraph"`, the child's whole definition under `graph`, recursively), and the validator recurses: each group needs at least one branch (`STRATA_ERR_EMPTY_GROUP`) with unique names (`STRATA_ERR_DUPLICATE_BRANCH`, `related_node` = the branch), and each child is validated as a graph of its own, its errors naming nodes by their qualified path (`Remediate/Abort`, `Remediate/Fix/Verify`). Errors come level by level: a level's own, then its groups', then each child's. Human output prints a duplicate branch as `Group/Branch`; the `--json` shape is unchanged. A hierarchical file is one file in directory mode, valid only if every level is.
- **`view` annotates composite nodes** with one line each under the diagram (`Investigate: parallel group [Kubernetes, Prometheus, GitHub]`, `Remediate: subgraph, entry Plan, 4 nodes`). It doesn't draw the child; `view --json` prints the whole definition.
- **Dangling edges are an error** (`STRATA_ERR_DANGLING_EDGE`, `node` = the edge's `from`, `related_node` = its `to`): an edge naming something that is not a node, including a recovery-policy fallback to a missing node, which the export carries as an `on_failure` edge. For that one case `.compile()` fails earlier with its own error, so the CLI reports the fault as a validation error where `.compile()` reports it as a configuration error; the verdict (rejected) is the same.

**Gotcha, fixed by the export:** a compiled graph's own edge list (Rust `CompiledGraph::definition`, .NET `CompiledGraph<T>.Topology`) holds only the edges the executor routes over, with no fallback route. Writing *that* out makes a node reachable only through a recovery policy look like an orphan. Export with `to_definition()` / `ToDefinition()`.

**Not built:**

- ~~**Whole-system validation.**~~ Built with SG-09 (`design/22-Graph-Structure-In-Definitions.md`): a parent's export carries every group's branches and every child's definition, and `graph validate` checks them all.
- **Edge predicates and other runtime facts.** The export records each edge's `guarded` flag but not its condition text (the engine keeps none); interrupt boundaries and retry counts are not exported either. The only condition text is on the engine's synthetic edges: `on_failure` for a recovery-policy fallback, and `on_reject` for an interrupt boundary's reject route (`design/21-Typed-Human-Signals.md`), which `graph validate` checks like any guarded edge.
- **`.compile()`'s non-structural checks.** The CLI cannot see a policy on a non-fallible node, a timeout on a missing node, or a bad metadata key; `.compile()` rejects those (`CompilationFailed` / `InvalidOperationException`) before it validates. An empty parallel group and duplicate branch names are now visible in the export (SG-09), so the CLI reports them as `STRATA_ERR_EMPTY_GROUP` / `STRATA_ERR_DUPLICATE_BRANCH` while `.compile()` still fails first with its own error: same verdict, different error, as for a fallback to a missing node.
- ~~**Postgres and Redis for the other commands.**~~ Built with SG-11 (`design/19-Async-Queryable-Store.md`): `thread` and `checkpoint` take `--storage <file | postgres://… | redis://…>` and read through `strata-memory`'s query port, the same code the Rust runtime writes with. `thread list --status` filters on the thread's state, so a resumed thread lists as `resumed`, not `interrupted`.
